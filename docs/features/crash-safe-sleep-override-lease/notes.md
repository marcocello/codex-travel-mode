# Architecture research

## 2026-07-17 supported macOS helper boundary

Concrete question: which supported macOS mechanism can own a root-only, fixed `SleepDisabled` lease while authenticating the app and detecting loss of its connection?

Apple documents `SMAppService` for macOS 13 and later as the supported registration API for app-bundled LaunchDaemons. The daemon property list belongs at `Contents/Library/LaunchDaemons`, the executable may live at `Contents/Resources`, and `BundleProgram` addresses it relative to the containing app. LaunchDaemon registration requires administrator approval and exposes an authorization status; Travel Mode must therefore check that status and fail Start closed when registration, approval, launch, or connection is unavailable. Sources: [SMAppService](https://developer.apple.com/documentation/servicemanagement/smappservice), [updating helper executables](https://developer.apple.com/documentation/servicemanagement/updating-helper-executables-from-earlier-versions-of-macos), and [register](https://developer.apple.com/documentation/servicemanagement/smappservice/register()).

Apple documents XPC as the privilege-isolation and IPC boundary for launchd services. `NSXPCListener.setConnectionCodeSigningRequirement` is available from macOS 13 and enforces a code-signing requirement on incoming connections; `NSXPCConnection` invalidation reports that a connection terminated and cannot be re-established. Production will bind lease ownership to the authenticated XPC connection and its invalidation, not to a PID supplied in a request. Sources: [XPC](https://developer.apple.com/documentation/xpc), [listener code-signing requirement](https://developer.apple.com/documentation/foundation/nsxpclistener/setconnectioncodesigningrequirement(_:)), and [connection invalidation](https://developer.apple.com/documentation/foundation/nsxpcconnection/invalidationhandler).

Repo implication: package one narrowly scoped SMAppService LaunchDaemon and use a code-signing-restricted XPC protocol containing only acquire, resolve/status, release, acknowledge, and cleanup retry messages. The daemon alone reads and writes `SleepDisabled`, persists the original value in a root-owned helper journal, and reacts to connection invalidation. Deterministic proof may replace ServiceManagement approval, peer identity, and the final fixed power executable, but it must run the same lease state machine in a real helper subprocess and kill real owner/helper processes.

## Contract revision after quality review

The initial contract incorrectly collapsed all failed acquisition stages into Off, did not distinguish an unreachable helper from authoritative not-found, mentioned spoofed caller PIDs despite requiring connection ownership, allowed only one overwriteable receipt implicitly, and did not revoke an already-Active app after helper loss. It also claimed a production helper subprocess boundary that ordinary deterministic tests could not honestly provide without installing a root Mach service.

The repaired contract freezes seven criteria: authenticated durable acquire; exact restore and receipt-before-clear; owner-death/lost-response/restart recovery; connection-bound least privilege; idempotence with one active lease and independently retained receipts; app fail-closed plus Active revocation; and an honest process proof with packaged/live validation deferred. Transport/auth failure now throws and can never equal not-found. The helper state machine, principal, generation, receipt precedence, baseline-true drift behavior, and test connector are explicit before implementation begins.

A second quality pass required four more executable details. The authoritative feature now fixes the root-owned paths and permissions, journal fields/revision and write-ahead order; defines the five-second healthy owner-death deadline plus two-second failure publication and capped retry schedule with a clock seam; removes contradictory spoofed-PID/command requests in favor of typed-interface rejection and metacharacter pressure; and names `scripts/validate_helper_packaging` with exact bundle, plist, identifier, signing-order, and proof-surface assertions.

## Proof-first failing baseline

Before changing the client contract or implementing the helper, `docs/features/crash-safe-sleep-override-lease/proof/run.sh` executed `SleepOverrideLeaseProcessProofTests.testUnavailableHelperCannotMasqueradeAsAuthoritativeNotFound` against the prior code and failed. The observed defect was exact: `UnavailableSleepOverrideLeaseClient.resolve` returned `nil`, which the coordinator could interpret as authoritative not-found and use to clear ownership. The production contract was changed only after this failing boundary was captured; the regression now requires an unavailable helper to throw a typed pre-dispatch error, while authenticated authoritative not-found remains a distinct result.

## Implementation repair audit

The post-implementation audit found that connection invalidation could enter the helper before an already-dispatched acquire task. The focused regression failed by returning Active and leaving an override owned by a dead connection. The helper now tombstones invalidated server-created connection IDs before waiting for the serialized operation boundary and rejects a later acquire before baseline capture or mutation.

The same audit found two app recovery gaps: a protection-loss event could arrive after helper acquisition but before `TravelModeAppState` published Active, and an exact resolved `cleanup_required` receipt was rejected when the app journal did not yet contain its binding. The app now records protection loss throughout activation and recovers before starting work, while the coordinator persists any exact resolved binding and drives release. Focused app, coordinator, helper-engine, and XPC tests pass these paths.

A corrupt released receipt with an unsupported schema could previously be treated as authoritative and allow journal removal without baseline restoration. Receipt decoding now validates its schema, restoration treats a corrupt receipt as unsafe rather than committed, and a regression proves the baseline is restored while the active journal remains `cleanup_required`. That regression also exposed that direct `Date` equality is not a reliable durable read-back oracle after `secondsSince1970` encoding. The store now decodes and canonically re-encodes the bytes before accepting a write and returns the canonical read-back value.

Finally, the XPC event hub originally suppressed every interruption after the first one for a retained connection. A failing two-interruption regression established the false-Active risk. A confirmed successful XPC round trip now re-arms interruption delivery, while duplicate callbacks within the same interruption remain deduplicated.

The first full repository gate also found a shared proof-artifact publication race rather than a lease defect: the transactional host exposed `result.json` before `trace.json`, so the reader could observe an incomplete case. The host now publishes the result as the final atomic completion marker; the focused case passed 20 consecutive runs and the complete transaction suite passed before both affected evidence bundles were refreshed.
